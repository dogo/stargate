# Structured review output (JSON findings)

Split into two deliveries. **This plan implements V1 only.** V2 is specified at the end with
the evidence needed to decide it, and is deliberately not scheduled here.

## Context

The reviewer's entire contract today is one line of prose: `stages.py:729-738` takes the last
line of `review-N.md` and demands exactly `VERDICT: APPROVED` or `VERDICT: CHANGES_REQUESTED`.
Everything downstream is opaque text — the fixer receives raw prose as `{review}`,
`summary.md` shows no findings, `state.json` records only the verdict string. Findings remain
in the raw review artifacts but are not available as structured report data.

V1 makes the findings structured **without changing who decides approval.** The reviewer keeps
emitting an explicit verdict: V1 preserves its authority and the orchestrator's review/fix
rules. It does not promise identical verdicts or call counts from real agents. A new prompt
and rubric can change the reviewer's judgment, and malformed JSON introduces a new failure
case. Findings become data in `summary.md` and `state.json`; the fixer still receives the
original reviewer response, now JSON or prose.

V1 is worth delivering if someone will use the structured summary, or if a defined sample of
real runs will be examined to evaluate V2. In the latter case its purpose is measurement,
not a saving in fixer calls. Without a report consumer or a planned analysis, defer the
implementation rather than adding a contract solely because it might be useful later.
Once the findings table is in scope, persistence in `state.json` has an internal consumer:
the summary generated by an approved resume that skips the reviewer. It is required for
that path's correctness, independently of external tooling or V2 measurement.

Two things this plan deliberately does **not** claim:

- It does not "move the decision from the model to code". Even under V2's severity policy the
  model still supplies the input that determines the outcome — classifying a real defect as
  `low` approves it indirectly. The honest framing is that V2 would make the *policy* explicit
  and configurable; the decisive judgment stays with the model. A rubric improves consistency,
  it does not remove that.
- It does not assume the fixer-cycle saving is real. That saving is plausible, not measured;
  fake-agent tests can only prove the rule executes, never that real reviewers separate
  `medium` from `low` well. V1 produces structured observations; evaluating the policy also
  requires human review of selected findings and their context.

This is the first open item in the README's `## Useful next additions`.

## The V1 contract

`reviewer.md` becomes machine-readable, in the style `fanout.md` already established (a bare
JSON object, no prose around it). This example describes a hypothetical data-loss defect:

```json
{
  "verdict": "CHANGES_REQUESTED",
  "findings": [
    {
      "severity": "high",
      "file": "app/storage.py",
      "line": 42,
      "finding": "Saving truncates the existing file before validating the replacement.",
      "why": "Invalid input permanently destroys previously saved user data."
    }
  ]
}
```

- `verdict` (required): exactly `APPROVED` or `CHANGES_REQUESTED`. **It stands as given** —
  the orchestrator does not derive, override, or second-guess it.
- `findings`: list, may be empty. Each entry needs `severity` (`high` | `medium` | `low`,
  normalized case-insensitively) and a non-empty `finding`. `file`, `line` (integer), `why`
  are optional.
- Unknown keys are ignored, for forward compatibility with V2.
- `CHANGES_REQUESTED` with an empty `findings` list is accepted, not an error. Enforcing
  coherence between verdict and findings is the V2 policy wearing a disguise; keep it out.

`severity` is collected and reported but **acts on nothing** in V1. Its job is to make the
report legible and to accumulate the sample V2 needs.

## Severity rubric

The packaged `reviewer.md` carries these definitions so the recorded data is consistent enough
to be worth analyzing later. Classify demonstrated impact, never the size or convenience of
the fix.

- **high**: a defect that can lose or corrupt user data, expose secrets, allow unauthorized
  access, or make a core workflow unusable under normal supported use. Name the trigger and
  the concrete harm; the example above belongs here.
- **medium**: an actionable correctness defect, regression, or unmet task requirement with
  bounded impact, including a supported edge case that produces wrong results. It needs a fix
  even when the common path works. Failing configured tests are at least `medium`.
- **low**: a cosmetic, readability, or documentation improvement with no demonstrated
  correctness, security, data-integrity, or task-requirement failure.

Preference alone does not justify `medium`, and a defect with a concrete failing scenario must
not be demoted to `low` because its fix is small. In V1 no severity changes what the
orchestrator does, which is exactly why the rubric can be introduced now and measured before
any policy depends on it.

## Implementation

No new module — the parser lives next to its only consumer, as `parse_task_graph` lives in
`fanout.py`.

**`stargate/core.py`**: `RunContext` gains an explicit
`findings: list[dict[str, Any]] = field(default_factory=list)`, separate from `review`.

`review` is a **checkpoint**: transient control state (`attempt`,
`verdict`, `fingerprint`, `fixed`) that exists to re-enter an interrupted loop and is
meaningless once the run finishes. Findings are a **report**: they must survive to the
terminal state. Separate fields let the existing checkpoint cleanup leave the report intact.

`findings` holds only the most recent completed review's findings. A later review replaces
it; it does not describe subsequent edits that have not been reviewed. Per-pass analysis uses
the saved `review-N.md` artifacts, not a new history array in `state.json`.

**`stargate/run.py`**: serialize and restore `findings` in `save_state()` / the state loader
alongside `review`. A `state.json` written before this change has no key; default to `[]`.

An approved review whose commit failed is the concrete consumer of this persistence.
With an unchanged fingerprint, `stages.py:685-691` skips the entire review loop and goes
straight to `finish()` → `write_summary()`. No reviewer invocation or artifact parsing
repopulates `ctx.findings` on that path. The state loader must restore them, or the resumed
run's summary loses its findings table despite having a valid review with findings.

**`stargate/stages.py`** (`finish`, `write_summary`, and the shared review/fix loop at
`stages.py:645-780`):

- `parse_review(raw) -> tuple[str, list[dict]]`. Tries `json.loads` first; on
  `JSONDecodeError` or a non-dict result, falls back to the current last-line check and
  returns `(verdict, [])`. When neither contract holds, one error naming both:
  `"Reviewer output is neither a JSON review object nor a response ending in VERDICT: …"`.
  Shape errors inside valid JSON raise precise `StargateError`s naming the offending index,
  mirroring `parse_task_graph` (`fanout.py:86-240`).
- In the loop, replace the two `last_line ==` branches with `parse_review(...)`. Keep passing
  the original reviewer response as the `review=` argument to the fixer's `render_prompt`,
  for both JSON and prose. V1 adds no dedicated fixer renderer or blocking/non-blocking
  labels. The fixer can read JSON; introduce a transformation only if actual use shows a
  problem with that input.
- `_record_review()` (`stages.py:617-631`) keeps its checkpoint role unchanged. Findings are
  assigned to `ctx.findings` in the loop instead, including on the `fixed=True` transition.
- `_recorded_review()` (`stages.py:633-643`) validates a reusable artifact by string equality
  on its last line. It must accept a JSON artifact too: parse with `parse_review` and keep the
  text only when the result is `CHANGES_REQUESTED`. Missing or malformed artifacts still
  return `None` so a real review replaces them.
- `finish()` keeps its existing cleanup rules: clear the checkpoint when the commit did not
  fail, and preserve it with the fingerprint refresh when the commit failed. Leave
  `ctx.findings` intact in both cases. A finished run reports findings without advertising
  an active review/fix checkpoint.
- `write_summary()` gains a `## findings` table (severity | file:line | finding) from
  `ctx.findings`, using the existing `_summary_cell` escaping. Human-readable formatting
  belongs here; no shared renderer is needed.

**`stargate/prompts/reviewer.md`**: rewritten around the JSON contract and the rubric. Keeps
`{task} {base_ref} {plan} {tests}` and the existing instruction to run the configured test
command itself when its tools allow.

The existing `fixer.md` instruction, "address every valid actionable finding", applies to
both JSON and prose and needs no change. V1 adds no findings trailer and does not touch
`commit.py`; the summary and state provide the report surfaces.

Artifacts stay `review-N.md` even when they hold JSON. Renaming breaks `resume` for every run
already on disk and churns dozens of doc and test references for nothing.

## Back-compat, which is not optional here

A run created before this change has its prompts **frozen** in
`.stargate/runs/<id>/prompts/` (`run.py`, snapshotted at run start) and `resume` uses that
copy. Its reviewer asks for prose. The prose path is therefore what keeps in-flight runs
resumable — not a courtesy to old configs, and the same reason a user's custom `prompts_dir`
reviewer keeps working untouched. A `state.json` from such a run has no `findings` key and a
checkpoint without findings; both must load.

Because V1 introduces no policy setting, resuming with `--config` cannot change a recorded
verdict. That whole class of interaction arrives only with V2.

## Tests — `tests/test_review_findings.py` (new module, no registry to edit)

Fake reviewers are `/bin/sh -c` scripts that `cat` a JSON file, following the
`agent(f'cat {graph}')` idiom used for fan-out graphs.

1. `test_json_findings_reach_the_summary_and_the_final_state` — the new report surfaces,
   including a `low` finding under an `APPROVED` verdict, which today stays only in prose.
2. `test_the_fixer_receives_the_original_json_review` — assert the prompt the fixer actually
   received contains the original JSON response, including the verdict and finding details,
   without a rendered replacement or invented blocking labels.
3. `test_a_prose_reviewer_still_reaches_both_verdicts` — back-compat, including a resume with
   legacy frozen prompts and a checkpoint written without findings.
4. `test_malformed_review_output_names_both_contracts` — bad JSON, a missing/invalid
   `verdict`, and a bad `severity` each produce a diagnosable error, and the run stays
   resumable.
5. `test_findings_survive_a_resume_without_a_second_review` — extends the fingerprint
   guarantee of `test_review_cycle.py` to the structured payload. Cover both an interrupted
   fixer reusing CHANGES_REQUESTED and an APPROVED review with findings whose commit failed.
   For the approved case, resume with the same fingerprint and assert the summary retains
   its findings while the reviewer invocation count stays unchanged: the table must be
   populated from restored state even though the review loop was skipped.
6. `test_a_finished_run_reports_findings_without_an_active_checkpoint` — the two lifetimes:
   after a terminal commit the findings are in `state.json` and the summary, no checkpoint
   attempt remains, and resuming again calls a fresh reviewer. Cover `--no-commit` too:
   findings still persist.
7. `test_an_explicit_verdict_is_never_overridden` — a `CHANGES_REQUESTED` carrying only `low`
   findings still blocks, and an `APPROVED` carrying a `high` finding still approves. This is
   the test that pins V1's scope and fails the moment V2 leaks in early.
8. `test_per_pass_artifacts_keep_findings_replaced_in_the_final_report` — review 1 requests
   changes for a low finding, the fixer changes the tree, and review 2 approves with no
   findings. Final state stores the emptied findings as `null` -- the convention the
   neighbouring `fanout` and `review` keys already use -- while `review-1.md` still contains
   the explicit CHANGES_REQUESTED verdict and low finding needed for the V2 sample.

Plus a docs test in the style of `tests/test_fanout_cli_docs.py`: the README documents the
contract and the packaged reviewer contains the rubric. The existing `test_review_cycle.py`
assertions remain valid: the checkpoint shape is unchanged and finished runs still clear it.

## V2, not scheduled: severity policy as opt-in

Would add `blocking_severities`, derive the verdict from the findings, and communicate which
entries are non-blocking to the fixer. Everything hard about it follows from that derivation:
prose reviews must keep their literal verdict regardless of the setting; the `medium`/`low`
boundary becomes load-bearing; a resume with `--config` can change the policy under a recorded
verdict, in both directions. Those are the cases to plan for when it is scheduled — plus the
cost to accept explicitly: **a misclassified severity can end a run before the fix.**

Do not pick a default from taste. If V1 is used to evaluate V2, define a sample of real runs
and inspect their available `.stargate/runs/*/review-*.md` artifacts with a one-off script.
Use each JSON review's explicit verdict and severities, retaining its run ID and pass number
so a human can inspect the finding and context. Prose-only or invalid artifacts are not
severity samples; report those exclusions rather than counting them as reviews with no
findings. No analysis tool or additional history schema is part of V1.

Do not use terminal `state.json` files to count earlier blocking reviews: review 1 can request
changes for a low finding, then review 2 can approve with `[]`. The final state intentionally
replaces that first result. Saved artifacts preserve the available passes, not an immutable
history of every resume; use a bounded sample and retain the reviewed artifacts/context for
the analysis rather than assuming missing or overwritten passes never happened.

The script selects cases; it does not decide whether the policy is safe:

1. How many `CHANGES_REQUESTED` reviews contained a non-empty set of **only** `low` findings?
   These are candidates for avoidable fixer cycles, not measured savings. Check whether a
   fixer actually ran and account for later passes of the same run; a different stopping
   policy would change that run's trajectory.
2. On human inspection of the findings and relevant code/task context, how many of those
   apparently low-only reviews contain real defects? These are cases where leniency could
   approve too early. JSON severity labels cannot answer this question by themselves.

If the first set is rare, the feature does not justify its complexity and V1 can stand alone.
If human inspection finds meaningful defects in that set, there is no basis for a lenient
default.

**There is no behavior-neutral derived default.** A lenient policy (`[high, medium]`) can
approve a low-only review whose explicit verdict requests changes. A strict policy
(`[high, medium, low]`) can block findings whose explicit verdict approves. Activating
either direction of V2 changes approval behavior; strictness is not a compatibility mode.
Keeping V1's explicit-verdict rule is the option that preserves the current approval
semantics. V2 needs an affirmative product decision backed by evidence, not just a choice
of severity default.

## First real-agent sample (2026-09-11)

Harvested from the runs that implemented findings inheritance and this policy, before
their artifacts were cleaned. Four reviews by `claude -p --model opus`, 13 findings. The
run ids and pass numbers are kept so the reasoning is traceable to `git log`, even though
the artifacts themselves are gone.

| run | pass | reviewer verdict | severities |
|---|---|---|---|
| `20260911-210529-findings-inheritance` | review-1 | APPROVED | low, low |
| `20260911-213254-severity-policy` | review-1 | CHANGES_REQUESTED | medium, low |
| `20260911-213254-severity-policy` | review-2 | CHANGES_REQUESTED | medium, low, low, low, low |
| `20260911-213254-severity-policy` | review-3 | APPROVED | low, low, low, low |

**Question 1 — `CHANGES_REQUESTED` reviews with only `low` findings: none.** Both blocking
reviews carried a `medium`. Both low-only reviews were approved by the reviewer on its own.

So in this sample the reviewer unaided already did what a lenient `[high, medium]` policy
would do, and that policy would have changed nothing. A strict `[high, medium, low]` policy
would have *blocked* both approvals, buying two fixer cycles for cosmetic findings.

**Question 2 does not arise:** the candidate set from question 1 is empty, so there is
nothing to inspect for real defects filed as `low`.

Four reviews from two runs by one model on one repository is far too small to decide a
default, and every finding came from reviewing this project's own code, which is not a
representative task mix. It is evidence that the question is worth asking rather than an
answer. What it does support: nothing here argues for changing the default away from
"the reviewer decides", and the strict direction looks actively worse.

## V3, unscheduled: the contract has nowhere to say "I could not verify this"

Observed across three real reviews on 2026-09-12, by `claude -p --model opus`, while the
reviewer's sandbox denied it permission to run `make test`:

| run | pass | shape the caveat took |
|---|---|---|
| `20260912-110044-task-sources` | review-1 | a `low` finding: "I could not independently execute `make test` or `make lint` in this worktree" |
| `20260912-190007-pull-requests` | review-1 | a `low` finding: "I could not verify the pasted test result" |
| `20260912-190007-pull-requests` | review-2 | **prose appended after the closing brace**, which broke the contract |

The third one cost real money: the object was complete and the verdict was `APPROVED`, but
`json.loads` refused the trailing sentence, the parser fell through to the prose contract, the
last line was not a `VERDICT:` line, and the run died. The paid review was discarded and had to
be bought again. Commit `208223b` made the parser tolerate a complete object with trailing
text, which stops the bleeding without addressing the cause.

**The cause is that the schema has no field for what the reviewer could not check.** The
packaged prompt tells it the test results "are a report, not evidence" and asks it to run the
command itself when its tools allow — so a reviewer that *cannot* has been given an
instruction it must report failing to follow, and no sanctioned place to report it. It
improvises: twice inside `findings`, once outside the object.

Neither improvisation is harmless. A caveat filed as a `low` finding pollutes the report — it
is not a defect in the code, it would be inherited as debt by a later run under findings
inheritance, and it would be counted as a finding by any severity policy. Prose outside the
object breaks the contract outright.

Questions a design would have to answer, none of them settled:

- Does the field belong at the top level (one statement about the whole review) or per finding
  (this specific claim is unverified)? The three samples are all whole-review statements.
- Does it affect anything, or is it report-only like `severity` is today? A reviewer that could
  not run the tests has arguably not met the packaged prompt's own bar, and a run might want to
  know that before publishing — which is the same "does data become policy" argument V2 has,
  and should not be answered by the same stroke.
- Is the real fix in the prompt rather than the schema? The instruction currently implies the
  reviewer should run the suite; softening it to "say so in this field if you could not" would
  change the improvisation into a contract without changing the parser.

Evidence note: the artifacts for the first two rows were on disk when this was written; the
third was overwritten when the run was resumed and the review re-bought, so its only durable
record is `208223b`'s commit message and this table.
